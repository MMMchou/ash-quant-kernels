# v0.2 step 2: multi-group K tiles + single-launch split-K (2026-10-16, H200)

Kernel: `ashqk/kernels/w4a16_gemm_v3.py`. Timing: `triton.testing.do_bench_cudagraph`
(L2 flushed between runs; matches how vLLM / SGLang run decode). Tests: GPU 117 passed, CPU interpreter 63 passed.

## What changed vs v2
1. `BLOCK_K` can span several quantization groups (scales/zeros loaded as `[NUM_G, BN]`, broadcast via a 3-D view).
2. Split-K in **one launch**: partials atomically added into a cached fp32 workspace; a per-tile arrival
   counter lets the last CTA write fp16 output and reset the workspace (CUTLASS-style serial fixup).
   v2 needed two extra kernels (zero-init + cast).

## Where the time goes (qkv_proj, M=1, ablation)

| config (BN, BK, SK, warps, stages) | full | no `tl.dot` | load only (no unpack/dot) |
|---|---|---|---|
| 128, 64, 8, 4, 2 | 19.7 us | 32.3 | 21.4 |
| 256, 128, 4, 4, 3 | 35.9 | 36.6 | 16.9 |
| 128, 256, 8, 8, 3 | 27.1 | 31.4 | **14.6 (896 GB/s)** |

Pure streaming of the same packed weights (`experiments/exp_layout.py`): **3.7 us = 3.4 TB/s** on the raw
AWQ layout, 3.5 us with a Marlin-style tiled repack. So:
1. **HBM is not the limit** and the AWQ layout is fine (repacking gains ≤ 15%).
2. The gap (~3.7 us → ~20 us) is **in-register work**: interleave expansion + per-group broadcast +
   layout conversion into the `tl.dot` operand layout, which Triton routes through shared memory.
   Bigger tiles load faster but convert slower — the best config is a compromise.
3. Tried and rejected: 8 nibble-sliced dots on the packed tile without interleave
   (`experiments/nibble_sliced_v4.py`): 31.7 us, slower.
