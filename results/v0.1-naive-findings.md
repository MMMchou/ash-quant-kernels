# v0.1-naive: findings (2026-10-15, H200)

Full sweep: [h200-v0.1-naive.md](h200-v0.1-naive.md) (default tiles 16×64×64, not tuned).

## Correctness
- Kernel rel. error vs fp32 ground truth: 2.71e-4 (M=1, 4096²) / 2.73e-4 (M=256, K=12288),
  identical to cuBLAS fp16 on the same dequantized weights.
- Mutation check: replacing the AWQ nibble order with sequential order gives rel. error 1.24 → tests catch layout bugs.
- vLLM `awq_gemm_triton` runs on our tensors unchanged (format compatible), rel. error 2.37e-3
  (~9× ours; it accumulates in fp16).

Tile sweep (BM, BN, BK, warps, stages) for v1 spans 230–1369 us at M=1: config matters, but even the best is 10× off fp16.

## Diagnosis → v0.2 plan
1. **Dequant arithmetic is not the bottleneck** (removing it saves only ~25%).
2. **Weight loading is**: v1 gathers each packed int32 8× (one per output column), so the
   B tile is a [BK, BN] int32 load (4 B/weight instead of 0.5 B/weight) plus a large layout
   conversion before `tl.dot`. vLLM loads [BK, BN/8] once and expands with `tl.interleave` → 3.4× faster.
3. Even vLLM's Triton path is 3× slower than fp16 at decode. Bandwidth floor for this layer
   (12.6 MB int4 + 0.5 MB scales/zeros at 4.8 TB/s) is ~2.7 us; fp16 floor is ~10.5 us.
   Target for v0.2: **beat fp16 cuBLAS at M ≤ 16**.

v0.2 order: load-once + interleave unpack → autotune → split-K for M ≤ 16 → profile with Proton / ncu.
