# v0.2 step 3: decode GEMV path — first win over fp16 (2026-10-16, H200)

Kernel: `ashqk/kernels/w4a16_gemv.py`; dispatcher `ashqk.w4a16_linear` (GEMV for M ≤ 2, else v3).
Tests: GPU 173 passed, CPU interpreter 92 passed. Timing: CUDA graph, L2 flushed.

## Idea
1. **No `tl.dot`, no interleave.** Packed tile `[BK, BN/8]` is expanded by broadcasting to
   `[BK, BN/8, 8]` with per-nibble shifts — elementwise only, so no register-layout conversion
   (the v3 bottleneck). Output column for (p, i) is `8p + AWQ_ORDER[i]`, still contiguous per p.
2. **Dequant factored out of the reduction**, per group g:
   `Σ_k x_k (q_kn − z_gn) s_gn = s_gn · (Σ_k x_k q_kn − z_gn · Σ_k x_k)` → one FMA per weight;
   zero / scale applied once per group. Bonus: fp32 throughout, error 2.1e-4 vs cuBLAS fp16 2.7e-4.
3. BLOCK_M rows per program so weights are reused across rows; split-K 16 with the single-launch fixup.

## Result: `w4a16_linear` vs fp16 cuBLAS, M = 1, us (`results/h200-v0.2-step3-cudagraph.md`)

| layer | fp16 | ashqk | speedup |
|---|---|---|---|
| qkv_proj 6144×4096 | 13.9 | **13.5** | 1.03× |
| o_proj 4096×4096 | 10.0 | **9.2** | 1.09× |
| gate_up_proj 24576×4096 | 50.2 | **48.6** | 1.03× |
| down_proj 4096×12288 | 29.8 | **21.5** | **1.39×** |

Progress on qkv_proj M=1: v1 230.6 (eager) → v2 22.9 → v3 19.8 → GEMV **13.5 us**.

## Limits (honest)
- M = 2: wins only on down_proj (26.9 vs 30.4); M ≥ 4: CUDA-core FMA throughput caps GEMV, v3 takes over,
  still 0.6–0.7× fp16. Per-shape tuned M=2 configs exist (qkv 15.5 us) but are not in the defaults.
- Achieved bandwidth is still only ~1.0–1.2 TB/s (20–25% of HBM); 4-bit's theoretical headroom is ~4×.
  The FMA + unpack instruction count per byte is now the limit.
- Large M (prefill, M = 256) untouched: 4–6× slower than fp16.
